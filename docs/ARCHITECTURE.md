# tastemap — архитектура, роадмап, риски

Статус: рабочий документ техлида. Дата: 2026-07-10.
Входные данные: `docs/SPEC.md` (MVP-скаффолд), исследование API-ландшафта от 2026-07-10
(Spotify Web API / источники превью / конкуренты, с проверкой источников), стратегический синтез.

Документ фиксирует решения, которые **отменяют часть SPEC.md**: Spotify OAuth перестаёт быть
основным входом (см. §2.1). SPEC остаётся действительным для структуры кода, движка и demo-режима.

---

## 1. Резюме и позиционирование

tastemap — онлайн-сервис «акустический портрет музыкального вкуса»: пользователь приносит свою
библиотеку из любого источника (Last.fm, GDPR-выгрузка Spotify, публичный плейлист, собственные
файлы), сервис сам скачивает 30-сек превью треков, извлекает акустические признаки (librosa:
tempo, тональность, minor score, bittersweet, тембр/brightness, энергия, onset rate), кластеризует
и строит карту настроений, сигнатуры и share-карточки. Ключевой факт рынка (исследование
2026-07-10): **ни один живой B2C-конкурент не анализирует реальный звук** — все либо считают
playcounts, либо доедают предвычисленные Spotify audio features, замороженные депрекацией
27.11.2024. При этом сам Spotify API для новых приложений фактически закрыт (5 пользователей в dev
mode с 02.2026, extended quota — только юрлицам с 250k MAU). Это и есть позиционирование:
единственный B2C с собственным акустическим анализом + платформонезависимость, в нише, куда
конкуренты войти не могут, потому что построены на закрывшейся платформе.

### Конкурентный ландшафт (из исследования, проверено 2026-07)

| Сервис | Суть | Статус 2026 | Анализирует реальный звук? |
|---|---|---|---|
| stats.fm | Статистика Spotify, импорт GDPR-истории, 15M+ юзеров | Жив, активен | Нет — playcounts + метаданные |
| Obscurify | «Обскурность» вкуса, mood против среднего | Жив (грандфазер) | Нет — предвычисленные Spotify features |
| Receiptify | Share-карточка «чек» из топ-треков | Жив; вход Spotify **и Last.fm** | Нет — только ранжирование метаданных |
| musictaste.space | Совместимость вкусов, «sound aura» | Жив (грандфазер) | Нет — Spotify features (valence/energy) |
| Chosic | Playlist Analyzer, mood/BPM инструменты | Жив (грандфазер), донаты | Нет — сохранённый доступ + накопленная база |
| volt.fm | Публичные профили, свой трекинг прослушиваний | Жив, Pro-подписка + реклама | Нет — поведенческий трекинг |
| Moodify | Плейлисты по audio features | **Мёртв** (HTTP 522) — ядро было на убитых endpoints | Нет — потому и не пережил |
| Icebergify | Мем-«айсберг» по popularity | Полужив, хронические 500-ки | Нет |
| Instafest | Постер фестивального лайнапа | Жив, Spotify-only | Нет |
| Pudding «judge my music» | Сатирический «ИИ-сноб» | Legacy без развития | Нет — шаблоны поверх метаданных |
| Tunebat / SongData | Key/BPM-справочник для диджеев | Живы | **Частично** — анализ загруженных файлов per-track, но не портрет вкуса |
| **tastemap** | Акустический портрет библиотеки из любого источника | — | **Да — librosa поверх реальных превью/файлов** |

B2B-слой (доказательство спроса на акустические фичи, см. §2.3): Cyanite (~290 EUR/мес + кредиты),
ReccoBeats (бесплатный, на донатах, без SLA), SoundStat (оплата за уникальный трек), FreqBlog
(GBP 0.17/1000 запросов), AcousticBrainz (закрыт 16.02.2022, дамп 7.5M треков CC0 — заморожен).

## 2. Ключевые решения

### 2.1. ГЛАВНЫЙ ПОВОРОТ: Spotify OAuth — не основной вход, а dev-режим

SPEC.md проектировался вокруг «логин через Spotify → топ-треки + saved + ISRC». Исследование
показывает, что это **юридически и практически нежизнеспособно** для публичного продукта:

Практика (источники: блог developer.spotify.com 2026-02-06, changelog february-2026,
quota-modes doc, TechCrunch 2026-02-06):
- С 11.02.2026 новые Development Mode приложения: **максимум 5 авторизованных пользователей**,
  **1 Client ID на разработчика**, владелец обязан иметь **Spotify Premium**; с 09.03.2026
  Premium/5/1 распространены и на существующие dev-приложения.
- Extended quota с 15.05.2025 — **только юридическим лицам** с активным запущенным сервисом и
  **минимум 250 000 MAU** (quota-modes doc). Chicken-and-egg: набрать 250k MAU на 5 тест-юзерах
  нельзя; разработчики сообщают о 6 отказах подряд (community thread 2025).
- audio-features / audio-analysis / recommendations / preview_url для новых приложений закрыты с
  27.11.2024 и **не восстановлены** на июль 2026 (блог 2024-11-27; dev.to/birrings 2026: «no
  waitlist, no public statement»).

Юридика (Developer Policy, developer.spotify.com/policy, проверено 2026-07-10):
- **III.13** прямо запрещает анализ и производные метрики: «Do not analyze the Spotify Content…
  including… creating new or derived listenership metrics, benchmarking… usage statistics, user
  metrics» — «портрет вкуса» из данных Spotify формально подпадает под формулировку.
- **III.14** запрещает ML-ingestion: «Do not use the Spotify Platform or any Spotify Content to
  train a machine learning or AI model or otherwise ingest Spotify Content into a machine learning
  or AI model» — кластеризация/эмбеддинги на данных Spotify — трактуемый риск.
- III.9 запрещает передачу данных Spotify в сторонние сервисы; III.11 — реплицирование core-опыта.

**Решение:** Spotify OAuth остаётся в коде только как dev-режим для 5 тест-юзеров (полезен для
отладки резолвинга ISRC через `external_ids.isrc` — поле живо, удаление откатили в march-2026
changelog). Ни один публичный флоу на него не завязан. Роадмап и лендинг его не рекламируют.

### 2.2. Мульти-источник входа = продуктовый ров

Все конкуренты Spotify-locked, а Spotify закрывается — значит, вход в tastemap строится сразу
мульти-источником. Приоритет:

| # | Источник | Что даёт | Обоснование из исследования |
|---|---|---|---|
| а | **Last.fm OAuth/API** | история скробблов, топ-треки, artist+title | открытый API; аудитория меломанов; Receiptify уже показывает вход через Last.fm (проверено 2026-07-10). Детали лимитов/ToS Last.fm — **проверить** (в исследование не входили) |
| б | **Импорт GDPR-выгрузки Spotify** | полная streaming history (JSON) | данные принадлежат пользователю, не API; рабочая модель stats.fm — импорт истории за разовые ~$5.99 (Plus), 15M+ юзеров |
| в | **Ссылка на публичный плейлист YouTube Music** | список artist+title без логина | нулевое трение, вирусный вход; реализовано в v0.2 (SPEC-v02-ytmusic.md): анонимное чтение метаданных через ytmusicapi; матч превью по artist+title (ISRC у YT-треков нет) — Deezer-search первым (50 req/5s), iTunes вторым (~20 req/min) |
| г | **Загрузка своих аудиофайлов** | полный librosa-анализ целого файла | никаких ограничений превью и чужих ToS; путь для DJ/Bandcamp-аудитории, которую не обслуживает никто (Tunebat делает только per-track lookup) |
| д | Spotify OAuth (dev mode) | топ-50 + saved + ISRC | только 5 тест-юзеров, см. §2.1 |

Лестница YouTube Music (домашняя платформа основателя, поэтому приоритет):
1. **v0.2 — плейлист-ссылка** (реализуется): анонимные метаданные публичного/unlisted плейлиста;
   формально неофициальный клиент (риск — блокировки IP, не пользователи), read-only, низкие объёмы.
2. **v0.2+ — импорт Google Takeout**: пользователь сам выгружает свои данные YouTube Music
   (лайки/плейлисты/история) — юридически чистая модель, аналог GDPR-импорта Spotify. Формат файлов — **проверить**.
3. **v0.3 — официальный YouTube Data API v3 OAuth** (scope youtube.readonly): лайки (LL) и плейлисты;
   квота 10k units/день достаточна (playlistItems = 1 unit/50 треков); верификация Google для
   sensitive-scope — проходимый для инди процесс, в отличие от Spotify. Покрытие «лайков из
   YT Music» через Data API — **проверить** на реальном аккаунте.

Важно архитектурно: все источники сходятся в один нормализованный формат
`[{artist, title, isrc?, mbid?, played_count?}]` — движок и конвейер ниже не знают, откуда
пришла библиотека.

### 2.3. Превью-конвейер и канонический ключ трека

SPEC предлагал кэш по ISRC и «iTunes lookup по isrc». Исследование вносит две поправки:
(1) **iTunes lookup по ISRC не работает** — живые тесты 2026-07-10 возвращают resultCount:0,
параметра isrc в официальной документации lookup нет; (2) ISRC у нас теперь есть далеко не всегда
(Last.fm и плейлисты его не отдают).

**Решение — canonical-ключ и каскад резолвинга:**

- Канонический ключ трека = **нормализованный `artist + title`** (lowercase, юникод-нормализация,
  вырезание «(feat. …)», «- remaster» и т.п.) **+ ISRC/MBID, когда есть**. Кэш дескрипторов
  индексируется по обоим ключам.
- Каскад получения превью:
  1. Если есть ISRC → **Deezer `GET /track/isrc:{ISRC}`** — недокументированный, но рабочий
     endpoint (deezer-python docs); отдаёт `preview` (30-сек MP3) без ключа API.
     Лимит **50 запросов / 5 сек на IP** (error code 4 при превышении).
  2. Фолбэк → **iTunes Search API** по `term=artist+title&media=music` — `previewUrl`
     (~30 сек AAC .m4a), без аутентификации, лимит **~20 запросов/мин**
     (performance-partners.apple.com, подтверждено живым запросом 2026-07-10).
  3. Опционально (v0.3+) → **MusicBrainz** (1 req/s) как слой резолвинга artist+title→ISRC/MBID
     перед п.1, повышает точность матчинга.
  4. Резерв на масштаб → **Apple Music API**: документированный `filter[isrc]`,
     `attributes.previews[].url`; цена — Apple Developer Program $99/год + JWT. Включать, когда
     появится юрлицо/бюджет.
- Не-варианты (из исследования): Napster API — стриминг закрыт 01.01.2026; Odesli/Songlink —
  публичный API закрывается 31.07.2026; Spotify preview_url — null для новых приложений,
  workaround через embed-скрейпинг — вне ToS, не используем.
- **Анализ в памяти**: превью скачивается в память (или эфемерный tmp), librosa считает признаки,
  файл немедленно удаляется. Аудио **никогда** не пишется в постоянное хранилище, не проксируется
  и не раздаётся. Прецедент — AcousticBrainz, хранивший только дескрипторы «for copyright reasons».
- **Атрибуция iTunes**: там, где UI проигрывает превью, — бейдж/линк на магазин и подпись
  «provided courtesy of iTunes» (требование performance-partners). Если превью в UI не
  проигрываются вовсе (только анализ) — вопрос формы атрибуции **проверить** у юриста, см. §5.

### 2.4. Кэш дескрипторов = накапливающийся актив

- Популярный трек анализируется **один раз на всех пользователей**: кэш
  `features(canonical_key / isrc → JSON дескрипторов, версия движка, created_at)`.
  MVP — SQLite, v0.3 — Postgres.
- Храним **только невосстановимые дескрипторы** (числа: MFCC-статистики, tempo, key, спектральные
  метрики) — из них нельзя реконструировать аудио; это же юридическая минимизация (§5).
- Со временем кэш становится **B2B-активом**: спрос на «audio features как сервис» доказан рынком —
  ReccoBeats живёт на донатах при огромном трафике, SoundStat и FreqBlog продают то же за деньги,
  Cyanite берёт от 290 EUR/мес. tastemap может продавать доступ к своей базе фич (v1, §4).
- Бесплатный seed для холодного старта: дамп AcousticBrainz (7.5M треков, CC0) — **проверить**
  совместимость его Essentia-дескрипторов с нашим librosa-набором; в MVP не обязателен.

### 2.5. Монетизация (паттерны из исследования)

- **Freemium + разовая покупка ~$6** за глубокий анализ (полный импорт истории, расширенные
  разрезы) — модель stats.fm Plus ($5.99 one-time): разовый платёж снижает трение для вирусной
  аудитории.
- **Share-карточки** (карта настроений, «звуковая ДНК», bittersweet-профиль) как вирусный хук —
  общий паттерн категории (Receiptify/Instafest/Obscurify), но наши карточки построены на данных,
  которые нельзя скопировать за выходные.
- **Донаты** на старте (Ko-fi-модель Obscurify/Chosic/ReccoBeats).
- **B2B API фич** — v1, после накопления кэша (§2.4).

## 4. Роадмап

### v0.1 — MVP-скаффолд (сейчас, уже в работе)
Соответствует SPEC.md с поправкой §2.1.
- FastAPI-бэкенд (`service/backend`): движок признаков (адаптация analyze_audio.py),
  портрет-билдер, кэш SQLite, превью-каскад **Deezer-ISRC → iTunes artist+title**
  (поправка к SPEC: iTunes lookup по ISRC не работает — заменить на search по term).
- **Demo-режим** — `GET /api/demo/portrait` из готового CSV (448 лайков эксперимента): фронт
  разрабатывается и показывается без единого внешнего API.
- Spotify OAuth (PKCE) — как dev-режим, 5 тест-юзеров, только для отладки.
- Next.js-фронт: лендинг, скаттер-карта (SVG), карточки кластеров, bittersweet-блок.
- DoD — из SPEC: pytest зелёный, demo-portrait отдаёт контракт, фронт собирается и рисует.

### v0.2 — реальные пользователи без Spotify API
- **Last.fm вход**: OAuth/API-ключ, тянем топ-треки и историю скробблов → нормализатор.
  Перед стартом — **проверить** актуальные ToS/лимиты Last.fm API.
- **Импорт GDPR-выгрузки Spotify**: drag&drop ZIP/JSON `StreamingHistory*.json` /
  `endsong*.json`, парсинг на бэке, дедупликация по canonical key. UX-подсказка «как запросить
  выгрузку» (у Spotify это до 30 дней — **проверить** актуальный срок).
- **Share-card как картинка** (OG-image/серверный рендер SVG→PNG): карта настроений +
  fingerprint — главный вирусный хук.
- Ограничение объёма на бесплатном тарифе (например, последние N треков) — задел под $6-покупку.

### v0.3 — публичный запуск
- Домен, деплой: фронт — Vercel; бэкенд — Fly.io или Railway (librosa требует полноценный
  Python-рантайм, не serverless).
- **Postgres** вместо SQLite (кэш фич + пользователи + задания импорта).
- **Очередь** (RQ/Celery + Redis): асинхронный импорт больших историй, воркер с соблюдением
  rate limits (iTunes ~20/мин, Deezer 50/5с) и глобальным троттлингом на IP исходящих.
- Аккаунты (magic link/email), удаление данных по запросу (механика — с первого дня, §5).
- Монетизация: разовая покупка ~$6 (Stripe/Paddle — **проверить** доступность для ИП/самозанятого),
  донат-кнопка.
- Метрики/мониторинг (Sentry + простая продуктовая аналитика без сторонних трекеров на данных юзеров).

### v1 — B2B API фич
- Публичный API: `GET /features?isrc=…|artist=…&title=…` из накопленного кэша + асинхронный
  backfill отсутствующих треков (паттерн FreqBlog).
- API-ключи, тарифы per-track (паттерны рынка: SoundStat — за уникальный трек, FreqBlog —
  GBP 0.17/1000, Cyanite — от 290 EUR/мес: наш прайс между «бесплатным без SLA» ReccoBeats и Cyanite).
- К этому моменту — юрлицо и юридическая ревизия конвейера (§5): B2B-продажа фич повышает ставки
  относительно толерируемой B2C-серой зоны.

рамка легальности анализа — TDM-исключения ЕС / fair use США; механизм полного удаления данных
пользователя — с первого дня.

## 6. Открытые вопросы

1. **Last.fm API**: актуальные ToS, лимиты, требования к атрибуции, судьба OAuth-версии —
   исследование не покрывало, проверить до старта v0.2.
2. **Публичный плейлист без Spotify API**: легального программного способа читать чужой публичный
   плейлист у нового приложения нет (GET /playlists/{id} доступен, но в dev mode = 5 юзеров).
   Варианты: просить пользователя экспортировать плейлист сторонним инструментом; парсинг
   публичной веб-страницы (серая зона ToS). Решить до включения источника (в) в v0.2/v0.3.
3. **Атрибуция iTunes при «тихом» анализе**: требования Apple сформулированы для показа превью;
   обязательна ли атрибуция, если превью в UI не проигрываются, — проверить (пока планируем
   атрибуцию везде, где превью хоть как-то воспроизводятся).
4. **Seed из AcousticBrainz**: совместимы ли Essentia-дескрипторы дампа (CC0, 7.5M треков,
   заморожен на 07.2022) с нашим librosa-набором — эксперимент на выборке; возможно, не нужен.
5. **GDPR-выгрузка Spotify**: точный актуальный формат файлов (`StreamingHistory*.json` vs
   `endsong*.json`), сроки выдачи, есть ли ISRC внутри выгрузки — проверить на собственной выгрузке.
6. **Платёжный провайдер** для разовой покупки ~$6 с учётом юрисдикции владельца (Stripe/Paddle/
   LemonSqueezy) — проверить к v0.3.
7. **Версионирование движка**: при изменении алгоритма фич кэш инвалидируется (поле версии уже
   заложено в §2.4) — политика пересчёта (лениво/фоном) — решить в v0.3 вместе с очередью.
8. **Глобальные сравнения между пользователями**: где граница между «агрегированной анонимной
   статистикой tastemap» и «производной метрикой из данных платформ» — юрвопрос к моменту, когда
   появится функция процентилей против других пользователей.
