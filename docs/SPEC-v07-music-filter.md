# SPEC v0.7 — фильтр «только музыка» и снятие потолка глубины

Фидбек основателя (стоп-сигнал перед первым глубоким прогоном): (1) анализируются лайки
ВСЕГО YouTube, а не музыка — нужен музыкальный фильтр ДО расходования глубины;
(2) потолок 200 убрать — должен быть режим «все музыкальные лайки».

## A. Backend

### A1. Музыкальный фильтр источника youtube

- `app/sources/youtube_api.py`: этап отбора перед анализом:
  1. Паджинация playlistItems по LL — сканируем до конца плейлиста (или до безопасного
     максимума 5000 элементов), собираем videoId + videoOwnerChannelTitle + title;
  2. Батчами videos.list (id×50, part=snippet,contentDetails): оставляем
     `snippet.categoryId == "10"` ИЛИ владелец оканчивается на " - Topic";
     фильтр длительности >12 мин и недоступных — как раньше;
  3. Итог: хронологический (свежие первыми) список МУЗЫКАЛЬНЫХ лайков; limit применяется
     УЖЕ К НЕМУ.
- Прогресс: stage "fetching" получает подэтап-счётчик: progress.total/ done на время
  сканирования = просканировано/оценка (playlistItems totalResults), затем на этапе
  analyzing — как раньше (по отобранным). В payload прогресса добавить
  `music_found: int` (сколько музыкальных найдено на текущий момент сканирования).
- Квоты: скан 5000 = ~100 units playlistItems + ~100 units videos.list — ок в 10k/день;
  прокомментировать в коде.

### A2. Снятие потолка

- `POST /api/analyze/youtube`: `limit: int|null`; null или 0 = БЕЗ ЛИМИТА (все музыкальные).
  Валидация: отрицательные → 422. Для плейлиста/Takeout лимиты не трогаем в этой волне.
- `GET /api/youtube/summary` дополняется полем `likes_total` (как есть) и
  `note: "музыкальные отбираются автоматически при анализе"` — без предварительного
  скана (он дорогой по времени, делается в джобе).
- Джоба длинная (возможны часы на тысячах треков): в состояние джобы добавить
  `started_at` (ISO) и `rate_per_min` (скользящее по последним 20 трекам) — фронт
  посчитает ETA. In-memory джобы (умирают с рестартом бэка) — осознанное ограничение,
  зафиксировать комментарием; персистентность джоб — вне скоупа.

### A3. Тесты (без сети)

- фильтр: category 10 берётся, " - Topic" берётся, ролик категории 22 отбрасывается,
  >12 мин отбрасывается; limit применяется после фильтра; limit=0 → все;
- паджинация скана нескольких страниц; music_found в прогрессе;
- rate_per_min считается; 422 на отрицательный limit.

## B. Frontend

- Экран выбора глубины (source=youtube):
  - чипы: «Быстрый · 40» / «Глубокий · 200» / «Все музыкальные лайки · время зависит от
    их числа»;
  - подпись под сводкой: «{likes_total} лайков YouTube всего — музыкальные отберём
    автоматически (категория Music и треки YT Music)»;
  - подпись под кнопкой прежняя + «~2–4 сек на новый трек · повторные берутся из кэша».
- Прогресс: на этапе fetching — «Отбираем музыку из лайков… просканировано N из M ·
  найдено K музыкальных»; на analyzing — прежний прогресс + ETA из rate_per_min
  («осталось ~N мин»), обновлять не чаще раза в 5 сек, не показывать первые 30 сек
  (шумно). Поллинг-таймаут для безлимита: 90 мин.
- После done: «проанализировано N музыкальных лайков из K найденных».

## C. Definition of Done

1. pytest зелёный (вся сюита + новые), без сети.
2. Живой e2e НЕ по OAuth (сессии нет у ревьюера): замоканный полный цикл + живой прогон
   существующих потоков (demo 200, плейлист-джоба на коротком публичном плейлисте до done).
3. Фронт: сборка по правилу; SSR: экран глубины содержит «Все музыкальные лайки» и
   текст про автоотбор; grep — таймаут 90 мин для безлимита; ETA-логика с задержкой 30с.
4. Прежнее не сломано.
